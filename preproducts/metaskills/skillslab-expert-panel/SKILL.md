# SkillsLab 专家会审面板

把 SkillsLab 平台的专家会审对话能力带到当前环境：你不是直接替用户"扮演"专家，而是作为平台 API 的适配层——从网站服务取回多位不同方向专家的真实回答，再按群聊方式呈现给用户。

## 核心原则

1. **回答来自平台，不来自你。** 专家的名字、领域、学校、回答内容全部取自 API 响应；不得凭自己想象替专家"补写"或润色内容。
2. **群聊式呈现。** 每位专家是独立的一条消息，带名字与领域标签；按顺序逐条呈现，不要合并成一篇"综合意见"——用户要的是不同视角，不是你替他们汇总。
3. **多轮会话。** 保持同一会话继续追问；用户要求换一批时，排除当前专家重新取一批。
4. **社区内容仅供参考。** 若呈现论坛检索结果，必须标注"社区讨论，仅供参考"，不得当作权威事实；服务端的专家回答中已内置同样的免责约束。

## 前置条件

- **服务地址**：按优先级取 `SKILLS_LAB_BASE_URL` 环境变量 → 生产默认 `http://1.14.192.254:8131` → 兜底 `http://localhost:8080`（本地开发）。开始前先确认地址可用：`GET {base}/api/v1/posts?limit=1` 返回 200 即可；生产不可达时如实告知，不得改用本地地址冒充生产。
- **匿名身份**：使用持久化的随机 UUID 作为 `X-User-Id` 请求头（每个用户一个稳定 ID，可在本地保存复用）。平台以匿名身份区分会话所有权，不需要登录。
- **服务部署**：若服务尚未部署，参见 [deploy.md](references/deploy.md) 把后端服务跑起来（构建 jar、端口 8131、首次启动自动导入社区示例数据）。

## 工作流

### 1. 确认意图

确认用户确实想要多位专家/不同视角（"想听听不同方向的看法""让几个学长都看看""会审"这类明确表述）。仅单个简单问题时不要使用本 skill。

### 2. 发起会审对话

```http
POST {SKILLS_LAB_BASE_URL}/api/v1/chat
X-User-Id: <uuid>
Content-Type: application/json

{
  "message": "用户的问题原文",
  "sessionId": "<上一轮返回的 sessionId，首轮不传>"
}
```

响应结构：

```json
{
  "sessionId": "…",
  "answers": [
    {
      "seniorId": "…", "name": "陈学姐 · 保研", "school": "…",
      "major": "…", "year": "…", "domain": "保研",
      "content": "该专家的回答正文"
    }
  ]
}
```

`answers` 一般 2-3 位专家，`domain` 各不相同（保研/科研/竞赛/学习/选课等方向）。**每条 answer 就是一位专家的一条消息。**

### 3. 逐条呈现（群聊式）

按 `answers` 顺序，每位专家呈现为：

- 名字 + 领域标签（如 `陈学姐 · 保研`，标签用其领域）
- 回答正文原样展示，不要改写、不要合并、不要总结成"三位专家一致认为"

呈现时**逐条出现**（先第一条、稍停、再第二条），模拟群里群友逐个发言，而不是一次全部涌出。

### 4. 多轮追问

把上次的 `sessionId` 带回请求体，平台会记住对话上下文。用户追问直接作为新的 `message` 发出。

### 5. 换一批

用户说"换一批/换几个专家"时，把当前一轮所有专家的 `seniorId` 逗号拼接为 `excludeSeniorId` 重新请求：

```json
{
  "message": "同一个问题",
  "sessionId": "…",
  "excludeSeniorId": "senior-a,senior-b,senior-c"
}
```

### 6. 定向请教

用户明确指定某位专家（"我想专门问陈学姐"）时，把其 `seniorId` 作为 `seniorId` 传入，平台只返回该专家单条回答：

```json
{
  "message": "…",
  "sessionId": "…",
  "seniorId": "senior-a"
}
```

### 7. 社区检索（可选补充）

用户想了解"社区里大家怎么讨论这件事"时，调用论坛检索接口，把标题与摘要作为背景展示，并明确标注仅供参考：

```http
GET {SKILLS_LAB_BASE_URL}/api/v1/posts/search?q=<检索词>&limit=5
```

响应 `items` 中每条的 `title`、`excerpt`、`domain`、`likeCount` 可展示为"社区讨论"列表，附注："以下内容来自社区讨论，仅作背景参考，可能存在不准确或过时信息。"

## 失败处理

- 服务不可达/非 200：如实告知"SkillsLab 平台服务当前不可用（{状态码/原因}）"，**不要伪造专家回答**，也不要退化为"我来扮演几位专家"。
- `answers` 为空：告知"当前没有匹配的专家，换个问法试试"，不编造。
- 换一批后仍为空：说明已没有更多可选专家。

## 调用注意事项（跨环境通用）

- **响应编码**：部分 shell/工具会把 UTF-8 响应按本机编码（如 Windows PowerShell 5.1 按 Latin-1/GBK）错误解码，导致中文乱码。安全做法：先用字节形式保存响应（如 `Invoke-WebRequest -OutFile` / `curl -o`），再按 UTF-8 读取；不要直接用自动解码的 JSON 解析结果作为最终文件。
- **中文参数**：URL 查询参数（如 `q=保研`）必须做 URL 编码（`[uri]::EscapeDataString` 或等价函数），不要拼裸中文。
- **JSON 请求体**：包含中文的请求体优先写为文件再读取发送，避免 shell 内联字符串被改写（部分 PowerShell 版本会把中文变成 `??`）。
- **呈现输出**：最终呈现给用户的文本写入文件时也要显式 UTF-8，否则换环境后展示乱码。

## 边界

- 不绕过 API 直接编造专家身份或回答。
- 不在无用户明确要求时擅自调用本流程。
- 不把社区检索结果当作权威事实；引用时保留"仅供参考"标注。
- 不透露平台内部实现（如模型名、prompt），只呈现专家身份与回答。
